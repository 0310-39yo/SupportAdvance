# 完全なフロー：全フェーズ（A～O、19 段階）汎用版

**版:** 1.0 / 2026-06-26

---

## 0. 本書の位置づけと前提

本書は、クリーンアーキテクチャをベースとした開発プロジェクトにおける  
**仕様策定から実装・テストまでの全フェーズを定義する汎用作業手順書**である。

### AI の役割区分

本書では AI を製品名ではなく役割で表記する。

| 表記 | 役割 | 使用フェーズ |
|------|------|------------|
| **対話型 AI** | 思考整理・論点構造化・仕様書案作成 | Phase A（BoundedContext 向けパターン） |
| **検証・生成 AI** | 準拠チェック・文書自動生成・分析 | Phase A（技術共有型向けパターン）、C、D、D-2、F、I、K-1、L-1、M-0、N |
| **実装補助 AI** | プロンプト指示に基づく実装・テストコード生成 | Phase H、M |

### 適用タイプ

本フローは対象の性質に応じて **2 つのタイプ**に分かれる。  
タイプによって Phase A〜C の起点が異なる。

| タイプ | 対象 | Phase A の起点 |
|--------|------|---------------|
| **BoundedContext 型** | 独自の業務ドメインを持つコンテキスト | 要件・業務仕様からスタート（パターン 1・2） |
| **技術共有型** | 業務ドメインを持たない技術共有要素（Common / Crosscutting / SharedKernel） | 仕様メモ・参考プロジェクトの技術文書・ソースからスタート（パターン 3・4・5） |

## 2. タイプ別の起点と Phase A〜C の違い

### BoundedContext 型

独自の業務ドメインを持つコンテキスト。**要件・業務仕様を起点**として作業する。

```
【BoundedContext 型のフロー起点】

Phase A（パターン 1 or 2）
  ├─ パターン 1：要件テキスト → 対話型 AI → 業務仕様書案
  └─ パターン 2：既存プログラム → 検証・生成 AI → 技術仕様書元資料
      ↓
Phase B（人による承認）
      ↓
Phase D-2（対象オブジェクト一括列挙・設計文書生成）
      ↓
Phase C（対象オブジェクトの技術仕様書案生成）
      ↓
Phase D 以降...
```

**Phase C への入力：** 業務仕様書（確定版）

---

### 技術共有型

業務ドメインを持たない技術共有要素（Common / Crosscutting / SharedKernel）。  
**仕様メモ・参考プロジェクトの技術文書またはソース**を起点として作業する。

```
【技術共有型のフロー起点】

Phase A（パターン 3・4・5 のいずれか）
  ├─ パターン 3：参考プロジェクトのソースコード → 検証・生成 AI → 技術仕様書元資料
  ├─ パターン 4：参考プロジェクトの技術文書 → 検証・生成 AI → 技術仕様書元資料
  └─ パターン 5：自プロジェクトの仕様メモ → 検証・生成 AI → 技術仕様書元資料
      ↓
Phase B（人による内容確認・改修方針承認）
      ↓
Phase D-2（対象オブジェクト一括列挙・設計文書生成）
      ↓
Phase C（対象オブジェクトの技術仕様書案生成）
      ↓
Phase D 以降...
```

**Phase C への入力：** 技術仕様書元資料（確定版）＋ 自プロジェクトの設計ルール

> **📌 技術共有型の注意点**  
> 参考にした技術文書・ソースの設計思想を**そのまま移植しない**。  
> 自プロジェクトのアーキテクチャ・設計ルールに合わせて必ず改修する。  
> Phase B でこの「改修方針」を人が確認・承認する。

## 3. Phase A の詳細：4 つのパターン

Phase A は、作業の起点に応じて 4 つのパターンに分かれる。

---

### パターン 1：新規実装（要件から業務仕様書を作成） ― BoundedContext 向け

**状況：** 完全に新しい機能・モジュールを実装する場合

**担当：** 対話型 AI

**入力：** 要件テキスト・背景説明・制約条件

**処理：**
```
要件テキスト
  ↓
対話型 AI が思考整理・論点構造化
  ↓
業務仕様書案を作成
```

**出力：** 業務仕様書案

**例：**
```
要件：「ユーザー管理システムに LDAP 連携機能を追加したい」

↓ 対話型 AI が処理

出力：
# 業務仕様書案：LDAP 連携機能

## 全体概要
既存のユーザー管理システムに LDAP 認証をサポートする機能を追加する。
ローカル認証との併用を想定し、管理者が認証方式を選択可能にする。

## 機能 1: LDAP 認証
...
```

**フロー続行：**
```
業務仕様書案
  ↓
Phase B：人が確認・承認
  ↓
Phase D-2 → Phase C～E で設計文書を整理
```

---

### パターン 2：同一プロジェクト内の既存プログラム改修 ― BoundedContext 向け

**状況：** 同じプロジェクト内の既存プログラムを修正・拡張する場合

**担当：** 検証・生成 AI

**入力：** 既存プログラムファイル（自プロジェクト内）

**処理：**
```
既存プログラムを読み込み
  ↓
検証・生成 AI が実装内容を抽出・分析
  ↓
技術仕様書の元資料を自動生成
```

**出力：** 技術仕様書元資料（実装内容の抽出結果）

**例：**
```
入力ファイル：src/auth/auth.cs

↓ 検証・生成 AI が処理

出力：
# 技術仕様書元資料：auth モジュール

## 現在の実装内容

### 認証方式
- LDAP 認証：LdapAuthProvider.cs で実装
- ローカル認証：LocalAuthProvider.cs で実装

### セッション管理
- in-memory キャッシュを使用
- 有効期限：8 時間
...
```

**フロー続行：**
```
技術仕様書元資料
  ↓
Phase B：人が確認・承認
  ↓
Phase D-2 → Phase C～E で仕様書・設計書を整理
```

---

### パターン 3：他のプロジェクトのソースコードを参考にする ― 技術共有型向け

**状況：** 別のプロジェクトの実装を参考にして、共有コンポーネントを設計する場合

**担当：** 検証・生成 AI

**入力：** 他プロジェクトのプログラムファイル

**処理：**
```
他プロジェクトのプログラムを読み込み
  ↓
検証・生成 AI が実装パターン・設計思想を抽出
  ↓
技術仕様書の元資料を自動生成
```

**出力：** 技術仕様書元資料（参考実装の分析結果）

**例：**
```
入力ファイル：../project-x/src/shared/ValueObject.cs（他プロジェクト）

↓ 検証・生成 AI が処理

出力：
# 技術仕様書元資料：project-x の ValueObject 実装パターン（参考）

## 参考になる実装パターン

### 値等価性の実装方法
- GetEqualityComponents() による比較コンポーネント列挙
- Equals / GetHashCode の整合性

### 未設定状態の表現
- IsSet フラグによる Unset 状態の管理

## 注意事項
- project-x の実装はそのまま流用できない
- 自プロジェクトの設計ルールに合わせて改修が必要
```

**フロー続行：**
```
技術仕様書元資料
  ↓
Phase B：人が確認・承認（改修方針を含む）
  ↓
Phase D-2 → Phase C～E で仕様書・設計書を新規作成
```

---

### パターン 4：他のプロジェクトの技術文書を参考に改修して使用する ― 技術共有型向け

**状況：** 別のプロジェクトで作成された技術仕様書・詳細設計書・設計思想解説などを参考にして、  
自プロジェクトの設計ルールに合わせた技術共有コンポーネントを設計する場合

**担当：** 検証・生成 AI

**入力：** 他プロジェクトの技術文書（技術仕様書・詳細設計書・設計思想解説・ガイド等）

**処理：**
```
他プロジェクトの技術文書を読み込み
  ↓
検証・生成 AI が設計思想・ルール・制約を抽出
  ↓
自プロジェクトのアーキテクチャ・技術スタックとの差異を分析
  ↓
技術仕様書元資料（改修方針付き）を自動生成
```

**出力：** 技術仕様書元資料（参考文書の分析結果 + 改修方針）

**パターン 3 との違い：**

| 比較軸 | パターン 3 | パターン 4 |
|--------|-----------|-----------|
| 参考にするもの | ソースコード | 技術文書（仕様書・設計書） |
| 抽出内容 | 実装パターン・動作の詳細 | 設計思想・ルール・制約・判断の根拠 |
| 向いている場面 | 実装レベルの参考が必要な場合 | 設計レベルの思想・ルールを参考にしたい場合 |

**例：**
```
入力文書：
  - ../project-x/docs/技術仕様書/ValueObject技術仕様書.md
  - ../project-x/docs/guides/ValueObject_null処理設計思想解説.md

↓ 検証・生成 AI が処理

出力：
# 技術仕様書元資料：project-x の ValueObject 設計思想（参考）

## 参考になる設計ルール・思想

### null 排除の設計方針
- Domain 層は null を一切許容しない
- 未設定状態を IsSet = false のインスタンス（Unset）で表現
- Optional パターン（Maybe 型）を採用

### IOptionalValueObject インターフェースの設計
- From() と TryFrom() の使い分け（信頼できるソース / 外部入力で異なる）
- TryGetValue() による値の安全な取得

## 自プロジェクトへの改修方針（AI 案）

### そのまま採用できる点
- IsSet フラグによる Unset 状態の表現
- Optional パターンの採用方針

### 改修が必要な点
- C# バージョンが異なる場合：static abstract の有無を確認
- 名前空間・クラス名を自プロジェクトの命名規則に合わせる
- project-x 固有のプロジェクト制約は除去する

## 注意事項
- 技術文書の設計思想を参考にするが、自プロジェクトの設計ルールが優先される
- 参考文書の記述をそのまま自プロジェクトのルールとして採用しない
- Phase B で改修方針を人が確認・決定する
```

**フロー続行：**
```
技術仕様書元資料（改修方針付き）
  ↓
Phase B：人が確認・承認（改修方針の妥当性を判断）
  ↓
Phase D-2 → Phase C～E で自プロジェクト向け仕様書・設計書を新規作成
```

---

### パターン 5：自プロジェクトの仕様メモを起点にする ― 技術共有型向け

**状況：** 設計の議論メモ・アイデアメモ・会議メモなど、  
正式な仕様書ではないが設計の種となる情報が自プロジェクト内に存在する場合

**担当：** 検証・生成 AI

**入力：** 仕様メモ（設計議論のメモ・アイデアメモ・会議メモ等）

**処理：**
```
仕様メモを読み込み
  ↓
検証・生成 AI が断片的な記述を整理・構造化
  ↓
欠落している観点・未確定事項を明示
  ↓
技術仕様書元資料（構造化済み + 未確定事項一覧付き）を生成
```

**出力：** 技術仕様書元資料（構造化済み + 未確定事項一覧付き）

**パターン 1・3・4 との違い：**

| 比較軸 | パターン 1 | パターン 3 | パターン 4 | パターン 5 |
|--------|-----------|-----------|-----------|-----------|
| 起点の出所 | 自プロジェクト | 他プロジェクト | 他プロジェクト | 自プロジェクト |
| 内容の完成度 | 正式な要件 | 実装済みコード | 確定済み文書 | **非公式・断片的** |
| AI の主な役割 | 仕様書案の作成 | 実装の抽出 | 設計思想の抽出 | **整理・構造化・欠落補完** |
| タイプ | BoundedContext | 技術共有型 | 技術共有型 | 技術共有型 |

**例：**
```
入力メモ（断片的な議論メモ）：
  - ValueObject は null を返さない方針で行く
  - Unset みたいな概念が必要かも
  - From と TryFrom を分けると良さそう
  - DB からの値と UI からの値で扱いが変わる
  - C# 11 の static abstract が使えるはず

↓ 検証・生成 AI が処理

出力：
# 技術仕様書元資料：ValueObject 設計（仕様メモより構造化）

## 確定している設計方針
- Domain 層は null を返さない
- 未設定状態は Unset インスタンスで表現する
- 値の生成メソッドを信頼できるソース用（From）と外部入力用（TryFrom）に分離する
- C# 11 の static abstract を活用する

## 未確定事項（Phase B で人が決定する）
- Unset の具体的な表現方法（IsSet フラグ / 専用型 / その他）
- DB NULL と UI の未入力の扱いの具体的な差異
- TryFrom の戻り値の型（bool / Result<T> / その他）

## 要確認事項（AI が不明と判断した箇所）
- 「From と TryFrom を分けると良さそう」の根拠・意図
- static abstract の C# バージョン要件の確認
```

**フロー続行：**
```
技術仕様書元資料（構造化済み + 未確定事項一覧）
  ↓
Phase B：人が未確定事項を決定・承認
  ↓
Phase D-2 → Phase C～E で仕様書・設計書を作成
```

> **📌 パターン 5 の注意点**  
> 仕様メモは断片的なため、AI が整理した内容に**誤解・補完ミス**が含まれる可能性がある。  
> Phase B では「整理の正確性」と「未確定事項の決定」の両方を人が確認する。

## 5. Phase A 開始前チェックリスト

```
【Phase A 開始前に確認】

□ BoundedContext 型 か 技術共有型 か？

□ BoundedContext 型（パターン 1・2）の場合：
  □ パターン 1（新規）：
    □ 要件テキストが揃っているか
    □ 背景・制約条件が明確か
    → 対話型 AI で処理

  □ パターン 2（既存改修）：
    □ 対象プログラムファイルを特定したか
    □ ファイルパスが正確か
    → 検証・生成 AI で処理

□ 技術共有型（パターン 3・4・5）の場合：
  □ パターン 3（参考ソース）：
    □ 参考にするソースファイルを特定したか
    □ 自プロジェクトの設計ルールとの差異を把握しているか
    → 検証・生成 AI で処理

  □ パターン 4（参考技術文書）：
    □ 参考にする技術文書を特定したか
    □ 文書が最新・確定版であるか
    □ 自プロジェクトの設計ルールとの差異を把握しているか
    → 検証・生成 AI で処理
    → Phase B で改修方針を必ず人が確認・決定する

  □ パターン 5（仕様メモ）：
    □ 対象の仕様メモを特定したか
    □ メモの作成背景・議論の文脈を把握しているか
    → 検証・生成 AI で処理（整理・構造化・欠落補完）
    → Phase B で「整理の正確性」と「未確定事項の決定」を必ず人が確認する
```

> **D-2 と Phase C/D の関係**  
> Phase D-2 ではすべてのオブジェクトの個別設計文書を一括生成する。  
> 各オブジェクトの Phase C/D はこの D-2 出力を起点とし、必要に応じて確認・補完した上で Phase E（承認）へ進む。  
> D-2 が未実施の層・オブジェクトについては、Phase C（個別技術仕様書の新規生成）を起点とする。

## 9. 人の判断点（Decision Points）：全 8 つ

| 判断点 | フェーズ | 内容 | 選択肢 |
|---|---|---|---|
| **判断 1** | **Phase B** | 業務仕様書 / 技術仕様書元資料の承認（BoundedContext 型: 業務仕様書 / 技術共有型: 技術仕様書元資料 + 改修方針） | 承認 / 修正して再承認 |
| **判断 2** | **Phase E** | 技術仕様書 + 詳細設計書の承認 | 承認 / 修正して再承認 |
| **判断 3** | **Phase G** | 実装プロンプトの承認 | 承認 / 修正して再承認 |
| **判断 4** | **Phase J** | 実装コードの合格判定 | 合格 / 違反対応（修正指示） |
| **判断 5** | **Phase K-2** | テスト仕様書の承認 + テストレベル指定 | 承認 / 修正して再承認 + レベル指定（単体 / 結合 / システム / 複数） |
| **判断 6** | **Phase L-2** | 【指定レベル】テスト仕様書の承認 | 承認 / 修正して再承認 |
| **判断 7** | **Phase M-1** | テスト実装プロンプトの承認 | 承認 / 修正して再承認 |
| **判断 8** | **Phase O** | 最終判定 | 完了 / 指定フェーズに戻す |

## 10. 修正ループの例

### ループ 1：Phase E で「技術仕様書の修正が必要」

```
Phase E：人が確認 → 「修正必要」判定
  ↓
技術仕様書を修正
  ↓
Phase F：修正版から実装プロンプト案を再生成
```

### ループ 2：Phase I で実装違反を検出

```
Phase I：検証・生成 AI が違反検出
  ↓
人が修正方針を判定
  ↓
実装補助 AI または手動で実装コードを修正
  ↓
Phase I 再実行：準拠チェック
```

### ループ 3：Phase N でテスト失敗

```
Phase N：テスト実行 → 一部テスト失敗
  ↓
人が「テストコード修正」or「実装修正」を判定
  ↓
修正 → Phase N 再実行
```

## 11. フローの特徴

| 視点 | 特徴 |
|---|---|
| **対応タイプ** | BoundedContext 型 / 技術共有型（Common・Crosscutting・SharedKernel）の 2 タイプに対応 |
| **Phase A パターン数** | 5 パターン（新規 / 既存改修 / 参考ソース / 参考技術文書 / 仕様メモ） |
| **自動化の段階数** | 10 フェーズで AI が自動生成（A, C, D, D-2, F, I, K-1, L-1, M-0, N） |
| **人の判断点** | 8 つの判断点で承認・判定 |
| **ドキュメント連鎖** | 仕様 → 技術仕様 → 詳細設計 → 実装 → テスト仕様 → テスト実装 |
| **品質保証** | 各実装・テストフェーズで自動検証（I, N） |
| **トレーサビリティ** | 全フェーズが仕様から実装まで整合性を保証 |
