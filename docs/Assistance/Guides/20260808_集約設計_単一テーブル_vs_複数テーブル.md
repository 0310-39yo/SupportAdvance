# 集約設計：単一テーブル vs 複数テーブル

複数テーブルから構成される集約の設計パターン。Items と ItemNames テーブルの例を用いて、2つの設計アプローチを比較します。

---

## 📋 前提：テーブル構成

```
Items テーブル
├─ row_id (PK, 物理キー)
├─ item_code (商品コード)
└─ price (価格)

ItemNames テーブル
├─ row_id (PK, 物理キー)
├─ item_code (FK, Items と結合)
└─ name (商品名)
```

**要件:** Items の価格と ItemNames の名前を組み合わせて表示する集約を作成

---

## 🏗️ パターン1：複数テーブル集約（推奨される場合）

### 設計概要

```
ItemList (AggregateRoot)
├─ Item (Entity) ← Items テーブル
│  ├─ ItemCode (ValueObject)
│  └─ Price (ValueObject)
│
└─ ItemName (Entity) ← ItemNames テーブル
   ├─ ItemCode (ValueObject)
   └─ Name (ValueObject)
```

### 実装例

#### 集約ルート

```csharp
public class ItemList : AggregateRoot<ItemListId>
{
    private Item _item;          // ← Items テーブル
    private ItemName _itemName;  // ← ItemNames テーブル

    public Item Item => _item;
    public ItemName ItemName => _itemName;
    
    // プロキシプロパティ（表示層での利便性）
    public ItemCode ItemCode => _item.ItemCode;
    public Price Price => _item.Price;
    public string Name => _itemName.Name;

    /// <summary>
    /// コンストラクタ
    /// </summary>
    public ItemList(
        ItemListId id,
        Item item,
        ItemName itemName,
        IClock? clock = null)
    {
        ArgumentNullException.ThrowIfNull(id);
        ArgumentNullException.ThrowIfNull(item);
        ArgumentNullException.ThrowIfNull(itemName);

        Id = id;
        _item = item;
        _itemName = itemName;

        if (clock != null)
        {
            RaiseDomainEvent(new ItemListCreatedEvent(
                DomainEventId.New(),
                this.Id,
                clock.JstNow
            ));
        }
    }

    /// <summary>
    /// 名前を更新（ItemNames テーブルのみ変更）
    /// </summary>
    public void UpdateName(string newName, IClock clock)
    {
        ArgumentNullException.ThrowIfNull(newName);
        ArgumentNullException.ThrowIfNull(clock);

        var oldName = _itemName.Name;
        _itemName.UpdateName(newName, clock);

        RaiseDomainEvent(new ItemNameUpdatedEvent(
            DomainEventId.New(),
            this.Id,
            oldName,
            newName,
            clock.JstNow
        ));
    }

    /// <summary>
    /// 価格を更新（Items テーブルのみ変更）
    /// </summary>
    public void UpdatePrice(Price newPrice, IClock clock)
    {
        ArgumentNullException.ThrowIfNull(newPrice);
        ArgumentNullException.ThrowIfNull(clock);

        var oldPrice = _item.Price;
        _item.UpdatePrice(newPrice, clock);

        RaiseDomainEvent(new ItemPriceUpdatedEvent(
            DomainEventId.New(),
            this.Id,
            oldPrice,
            newPrice,
            clock.JstNow
        ));
    }
}
```

```csharp
    }
}
```

### Repository での保存処理

```csharp
public class ItemListRepository : IItemListRepository
{
    private readonly DbConnection _connection;
    private readonly IMapper _mapper;

    /// <summary>
    /// ItemList を保存（Items と ItemNames の両テーブルを更新）
    /// </summary>
    public async Task SaveAsync(ItemList aggregate, CancellationToken cancellationToken)
    {
        using var transaction = _connection.BeginTransaction();
        
        try
        {
            // Item テーブルを更新
            await UpdateItemAsync(aggregate.Item, transaction);
            
            // ItemName テーブルを更新
            await UpdateItemNameAsync(aggregate.ItemName, transaction);
            
            transaction.Commit();
        }
        catch
        {
            transaction.Rollback();
            throw;
        }
    }

    /// <summary>
    /// Items テーブルを更新
    /// </summary>
    private async Task UpdateItemAsync(Item item, DbTransaction transaction)
    {
        var dbModel = _mapper.ToItemDbModel(item);
        
        await _connection.ExecuteAsync(
            @"UPDATE [dbo].[t_items]
              SET [price] = @Price,
                  [updated_at] = @UpdatedAt,
                  [updated_by] = @UpdatedBy,
                  [row_version] = DEFAULT
              WHERE [row_id] = @RowId",
            new
            {
                Price = dbModel.Price,
                UpdatedAt = dbModel.UpdatedAt,
                UpdatedBy = dbModel.UpdatedBy,
                RowId = dbModel.RowId
            },
            transaction: transaction
        );
    }

    /// <summary>
    /// ItemNames テーブルを更新
    /// </summary>
    private async Task UpdateItemNameAsync(ItemName itemName, DbTransaction transaction)
    {
        var dbModel = _mapper.ToItemNameDbModel(itemName);
        
        await _connection.ExecuteAsync(
            @"UPDATE [dbo].[t_item_names]
              SET [name] = @Name,
                  [updated_at] = @UpdatedAt,
                  [updated_by] = @UpdatedBy,
                  [row_version] = DEFAULT
              WHERE [row_id] = @RowId",
            new
            {
                Name = dbModel.Name,
                UpdatedAt = dbModel.UpdatedAt,
                UpdatedBy = dbModel.UpdatedBy,
                RowId = dbModel.RowId
            },
            transaction: transaction
        );
    }
}
```

### メリット

✅ **変更の粒度が分離される**

- 名前変更と価格変更を独立してトラッキング
- 各テーブルの row_version で楽観ロックを個別管理

✅ **権限管理が柔軟**

- 名前を更新する権限と価格を更新する権限を分離可能
- 監査ログで「誰がどのテーブルを変更したか」が明確

✅ **パフォーマンス**

- 名前のみ変更する場合、ItemNames テーブルのみ UPDATE
- Items テーブルへの不要なアクセスがない

✅ **変更頻度の最適化**

- 名前はよく変わるが価格は変わらない場合、効率的
- 各テーブルのインデックスやロックを独立して最適化

### デメリット

❌ **実装の複雑性**

- Entity が複数になり、コードが増える
- Repository での複数テーブル更新ロジックが必要

❌ **トランザクション管理**

- 複数テーブルの更新を1つのトランザクション内で管理
- 部分的な失敗に対する処理が必要

❌ **Mapper の複雑性**

- Items と ItemNames の両方をマッピングし、組み合わせる必要あり

---

## 🏗️ パターン2：単一集約（複数テーブルデータ）

### 設計概要

テーブルは Items と ItemNames の **2つが存在したまま** だが、集約レベルでは **単一の ItemList** として扱う設計

```
【テーブル構成】
Items テーブル + ItemNames テーブル（2つ存在）
     ↓
【集約設計】
ItemList (AggregateRoot) ← Item Entity にしない、単一の集約として統合
├─ ItemCode (ValueObject)
├─ Price (ValueObject から Items テーブル取得)
└─ Name (string から ItemNames テーブル読み込み)
```

### 実装例

```csharp
/// <summary>
/// ItemList - 単一集約（Item/ItemName Entity にはしない）
/// 【注意】テーブルは Items/ItemNames の2つだが、ドメイン層では単一の集約として扱う
/// </summary>
public class ItemList : AggregateRoot<ItemListId>
{
    private RowId _itemsRowId;       // Items テーブルの物理キー
    private RowId _itemNamesRowId;   // ItemNames テーブルの物理キー（読み込み用）
    private ItemCode _itemCode;
    private Price _price;            // Items テーブルから取得
    private string _name;            // ItemNames テーブルから取得

    public ItemCode ItemCode => _itemCode;
    public Price Price => _price;
    public string Name => _name;

    /// <summary>
    /// コンストラクタ
    /// </summary>
    public ItemList(
        ItemListId id,
        ItemCode itemCode,
        Price price,
        string name,
        RowId? itemsRowId = null,
        RowId? itemNamesRowId = null,
        IClock? clock = null)
    {
        ArgumentNullException.ThrowIfNull(id);
        ArgumentNullException.ThrowIfNull(itemCode);
        ArgumentNullException.ThrowIfNull(price);
        ArgumentNullException.ThrowIfNull(name);

        Id = id;
        _itemCode = itemCode;
        _price = price;
        _name = name;
        _itemsRowId = itemsRowId ?? RowId.New();
        _itemNamesRowId = itemNamesRowId ?? RowId.New();

        if (clock != null)
        {
            RaiseDomainEvent(new ItemListCreatedEvent(
                DomainEventId.New(),
                this.Id,
                clock.JstNow
            ));
        }
    }

    /// <summary>
    /// 名前を更新（ItemNames テーブルに反映）
    /// </summary>
    public void UpdateName(string newName, IClock clock)
    {
        ArgumentNullException.ThrowIfNull(newName);
        ArgumentNullException.ThrowIfNull(clock);

        var oldName = _name;
        _name = newName;

        RaiseDomainEvent(new ItemNameUpdatedEvent(
            DomainEventId.New(),
            this.Id,
            oldName,
            newName,
            clock.JstNow
        ));
    }

    /// <summary>
    /// 価格を更新（Items テーブルに反映）
    /// </summary>
    public void UpdatePrice(Price newPrice, IClock clock)
    {
        ArgumentNullException.ThrowIfNull(newPrice);
        ArgumentNullException.ThrowIfNull(clock);

        var oldPrice = _price;
        _price = newPrice;

        RaiseDomainEvent(new ItemPriceUpdatedEvent(
            DomainEventId.New(),
            this.Id,
            oldPrice,
            newPrice,
            clock.JstNow
        ));
    }
}
```

### Repository での保存処理

```csharp
public class ItemListRepository : IItemListRepository
{
    private readonly DbConnection _connection;
    private readonly IMapper _mapper;

    /// <summary>
    /// ItemList を保存（Items と ItemNames の複数テーブルを更新）
    /// 【重要】パターン2 は複数テーブルを更新する必要がある
    /// </summary>
    public async Task SaveAsync(ItemList aggregate, CancellationToken cancellationToken)
    {
        using var transaction = _connection.BeginTransaction();
        
        try
        {
            // Items テーブルを更新（price）
            await UpdateItemAsync(aggregate, transaction);
            
            // ItemNames テーブルを更新（name）
            await UpdateItemNameAsync(aggregate, transaction);
            
            transaction.Commit();
        }
        catch
        {
            transaction.Rollback();
            throw;
        }
    }

    /// <summary>
    /// Items テーブルを更新
    /// </summary>
    private async Task UpdateItemAsync(ItemList aggregate, DbTransaction transaction)
    {
        await _connection.ExecuteAsync(
            @"UPDATE [dbo].[t_items]
              SET [price] = @Price,
                  [updated_at] = @UpdatedAt,
                  [updated_by] = @UpdatedBy,
                  [row_version] = DEFAULT
              WHERE [row_id] = @RowId",
            new
            {
                Price = aggregate.Price.ToString(),
                UpdatedAt = DateTime.UtcNow,
                UpdatedBy = /* current user ID */,
                RowId = aggregate._itemsRowId /* private アクセス必要 */
            },
            transaction: transaction
        );
    }

    /// <summary>
    /// ItemNames テーブルを更新
    /// </summary>
    private async Task UpdateItemNameAsync(ItemList aggregate, DbTransaction transaction)
    {
        await _connection.ExecuteAsync(
            @"UPDATE [dbo].[t_item_names]
              SET [name] = @Name,
                  [updated_at] = @UpdatedAt,
                  [updated_by] = @UpdatedBy,
                  [row_version] = DEFAULT
              WHERE [row_id] = @RowId",
            new
            {
                Name = aggregate.Name,
                UpdatedAt = DateTime.UtcNow,
                UpdatedBy = /* current user ID */,
                RowId = aggregate._itemNamesRowId /* private アクセス必要 */
            },
            transaction: transaction
        );
    }
}
```

### メリット

✅ **集約設計がシンプル**

- Item Entity、ItemName Entity を作らない（単一の ItemList）
- ドメイン層の責務が明確（単一の集約オブジェクト）

✅ **可読性**

- 集約内のすべてのフィールドが対等（Item・ItemName に分離されていない）
- ビジネスロジックで「Items と ItemNames は1対1」という関係が明確

✅ **ドメインモデルの統一性**

- 名前と価格が同じ集約内で変更される（一貫性を保ちやすい）
- 両者の同期が自動的に保証される

### デメリット

❌ **複数テーブル更新が必要**

- Items テーブルと ItemNames テーブルの両方を UPDATE する必要あり
- Repository での複数テーブルトランザクション管理が必須
- 実装コストが増加（パターン1と同様）

❌ **集約内で矛盾が生じやすい**

- テーブルレベルでは Items と ItemNames が分離されている
- しかし、集約レベルでは単一として扱うため、部分的な更新ができない
- 「名前のみ変更」したくても、Items テーブルの行版もアップデートされる

❌ **監査ログが一貫性を欠く**

- Items テーブルと ItemNames テーブルで更新者・時刻が異なる可能性
- テーブルレベルではどちらがいつ更新されたか分かるが、集約レベルでは「1つのイベント」として扱われるため、矛盾が生じる

❌ **テーブルが分かれている理由に対応困難**

- テーブルが複数に分かれているのは通常、独立した変更理由がある（多言語、履歴管理など）
- パターン2 ではその理由を無視して単一集約として設計するため、要件変更に弱い

## 📊 選択基準

| 選択基準                   | パターン1（複数Entity集約） | パターン2（単一集約） |
| -------------------------- | ----------------------- | ------------------- |
| **テーブル構成**           | Items + ItemNames（2つ） | Items + ItemNames（2つ） |
| **集約構成**               | Item + ItemName Entity | 単一の ItemList（Entity に分離しない） |
| **変更粒度の分離**         | ✅ 高い                 | ❌ できない           |
| **権限管理の分離**         | ✅ 可能                 | ❌ 困難               |
| **実装の容易さ**           | ❌ 複雑                 | ✅ シンプル            |
| **テーブル分割理由への対応** | ✅ 対応可能           | ❌ 対応困難            |

### パターン1を選ぶべき理由

**以下のいずれかに該当する場合：**

1. **変更粒度が異なる**

   - 名前はよく変わるが、価格は滅多に変わらない
   - 各変更を独立して追跡する必要がある

2. **権限管理が必要**

   - 名前更新と価格更新の実行者が異なる
   - 監査要件で「誰が何を変更したか」が重要

3. **テーブル分割に正当な理由**

   - 将来的な拡張性（言語対応、履歴管理など）
   - パフォーマンス最適化

### パターン2を選ぶべき理由

**パターン2 は以下の場合に選択されるべきですが、実務上はあまり推奨されません：**

1. **テーブルが分かれている理由がない**

   - Items と ItemNames が業務的に強く結合している
   - テーブル分割に明確な理由がない場合

2. **ドメインモデルの統一性が優先**

   - 名前と価格は常に一貫性を保つべき
   - 2つの Entity に分離することが過設計に感じる場合

3. **実装チームが Entity 設計に不慣れ**

   - 複数Entity集約の設計・実装が難しい
   - シンプルな実装が求められる

**⚠️ 重要：** パターン2 は複数テーブルを更新する必要があるため、実際には **パターン1 と同程度かそれ以上の複雑性** を持ちます。テーブル分割に理由がある場合は、**パターン1（複数Entity集約）を強く推奨** します。

## 🔄 使用例

### パターン1：名前のみ変更

```csharp
// 1. 集約を取得
var itemList = await _repository.GetByCodeAsync(ItemCode.From("CODE001"));

// 2. 名前を変更（ItemNames テーブルのみ UPDATE）

// 3. 保存（複数テーブルトランザクション）
await _repository.SaveAsync(itemList);

// 結果：
// - Items テーブル：変更なし（row_version も変わらない）
// - ItemNames テーブル：name カラム更新、updated_at/updated_by 更新
```

### パターン2：名前のみ変更

```csharp
// 1. 集約を取得
var itemList = await _repository.GetByCodeAsync(ItemCode.From("CODE001"));

// 2. 名前を変更
itemList.UpdateName("新しい商品名", _clock);

// 3. 保存（複数テーブルトランザクション）

// - Items テーブル：row_version 更新（_itemsRowId の行のバージョンが上がる）
```

## ✅ チェックリスト

### パターン1 を選択した場合

- [ ] 各 Entity（Item, ItemName）が独立した ValueObject ID を持つ
- [ ] Repository で複数テーブル更新をトランザクション管理している
- [ ] Mapper で Items と ItemNames の行を正しく結合している
- [ ] ドメインイベントが各テーブルの変更を追跡している
- [ ] RowId がプライベート属性（テーブルの物理キーのみ）

### パターン2 を選択した場合

- [ ] 集約内のすべてのフィールドが同じ更新頻度
- [ ] Repository の SaveAsync が単純な UPDATE ステートメント
- [ ] テーブル設計に分割する理由がない
- [ ] 監査要件で細粒度のログが不要

## 🔄 参照から更新までのライフサイクル：楽観ロック実装

集約の参照・更新には標準的な流れがあります。楽観ロック（row_version による競合検出）を使用します。

### フェーズ1：参照（トランザクションなし）

参照時はトランザクションを開かず、row_version を取得して保持します。

```csharp
public async Task<ItemList> GetByCodeAsync(ItemCode code)
{
    // ✓ トランザクション開始なし（高速、ロックなし）
    
    // Items テーブル読み込み
    var itemDbModel = await _connection.QuerySingleAsync<ItemDbModel>(
        @"SELECT [row_id], [item_code], [price], [row_version]
          FROM [dbo].[t_items]
          WHERE [item_code] = @ItemCode"
    );
    // row_version = 2026-08-08 10:30:00 を取得
    
    // ItemNames テーブル読み込み（複数テーブル集約の場合）
    var itemNameDbModel = await _connection.QuerySingleAsync<ItemNameDbModel>(
        @"SELECT [row_id], [item_code], [name], [row_version]
          FROM [dbo].[t_item_names]
          WHERE [item_code] = @ItemCode"
    );
    // row_version = 2026-08-08 10:29:50 を取得
    
    // DbModel → Entity に変換（row_version も含む）
    var item = _mapper.ToItemEntity(itemDbModel);        // row_version 保持
    var itemName = _mapper.ToItemNameEntity(itemNameDbModel);  // row_version 保持
    
    // Entity → AggregateRoot に組み立て
    var aggregate = new ItemList(
        id: ItemListId.From(itemDbModel.Id),
        item: item,
        itemName: itemName
    );
    
    return aggregate;
}
```

**参照フェーズの特徴：**
- ✅ トランザクション不要
- ✅ ロックしない（他プロセスの更新を妨げない）
- ✅ 同時実行性が高い
- ✅ 各テーブルの row_version を保持

### フェーズ2：ビジネスロジック実行（トランザクション外）

読み込んだ集約に対してビジネスロジックを実行します。この間もトランザクションは開始しません。

```csharp
// Application層（UseCase など）
public class UpdateItemPriceUseCase
{
    public async Task Execute(ItemCode code, Price newPrice)
    {
        // 1️⃣ 集約を参照（トランザクションなし）
        var itemList = await _repository.GetByCodeAsync(code);
        // Items.RowVersion = 2026-08-08 10:30:00
        // ItemNames.RowVersion = 2026-08-08 10:29:50
        
        // 2️⃣ ビジネスロジック実行（Domain層、トランザクション外）
        itemList.UpdatePrice(newPrice, _clock);
        
        // この間に別プロセスが Items または ItemNames を更新していても
        // row_version で競合が検出される
        
        // 3️⃣ 集約を保存（後述）
        await _repository.SaveAsync(itemList);
    }
}
```

### フェーズ3：保存（トランザクション内、row_version チェック）

更新時のみトランザクションを開始し、row_version で楽観ロックを実装します。

#### パターン1：複数テーブル集約での実装

```csharp
public class ItemListRepository : IItemListRepository
{
    private readonly DbConnection _connection;
    private readonly IClock _clock;  // ← IClock を注入
    private readonly long _currentUserId;
    
    public ItemListRepository(DbConnection connection, IClock clock, long currentUserId)
    {
        _connection = connection;
        _clock = clock;
        _currentUserId = currentUserId;
    }
    
    public async Task SaveAsync(ItemList aggregate)
    {
        // ✓ トランザクション開始（複数テーブル更新を原子的に）
        using var transaction = _connection.BeginTransaction(
            IsolationLevel.ReadCommitted
        );
        
        try
        {
            // IClock から LocalDateTime を取得（Domain 層の規則に従う）
            var updatedAt = _clock.JstNow;
            
            // 1️⃣ Items テーブル更新（row_version チェック）
            var itemRowsAffected = await _connection.ExecuteAsync(
                @"UPDATE [dbo].[t_items]
                  SET [price] = @Price,
                      [updated_at] = @UpdatedAt,
                      [updated_by] = @UpdatedBy,
                      [row_version] = DEFAULT
                  WHERE [row_id] = @RowId
                    AND [row_version] = @OldRowVersion",  -- ← 楽観ロック条件
                new
                {
                    Price = aggregate.Item.Price.Value,
                    UpdatedAt = updatedAt.Value,  // LocalDateTime → DateTime に変換
                    UpdatedBy = _currentUserId,
                    RowId = aggregate.Item.RowId,
                    OldRowVersion = aggregate.Item.RowVersion  -- ← 参照時の値
                },
                transaction: transaction
            );
            
            // row_version が異なる場合、UPDATE は 0 rows affected
            if (itemRowsAffected == 0)
                throw new ConcurrencyException(
                    "このアイテムは別のユーザーが更新しています。" +
                    "最新のデータを再度読み込んでください");
            
            // 2️⃣ ItemNames テーブル更新（row_version チェック）
            var nameRowsAffected = await _connection.ExecuteAsync(
                @"UPDATE [dbo].[t_item_names]
                  SET [name] = @Name,
                      [updated_at] = @UpdatedAt,
                      [updated_by] = @UpdatedBy,
                      [row_version] = DEFAULT
                  WHERE [row_id] = @RowId
                    AND [row_version] = @OldRowVersion",  -- ← 楽観ロック条件
                new
                {
                    Name = aggregate.ItemName.Name,
                    UpdatedAt = updatedAt.Value,  // LocalDateTime → DateTime に変換
                    UpdatedBy = _currentUserId,
                    RowId = aggregate.ItemName.RowId,
                    OldRowVersion = aggregate.ItemName.RowVersion  -- ← 参照時の値
                },
                transaction: transaction
            );
            
            if (nameRowsAffected == 0)
                throw new ConcurrencyException(
                    "この名前は別のユーザーが更新しています。" +
                    "最新のデータを再度読み込んでください");
            
            // 3️⃣ 両方の更新が成功 → コミット
            transaction.Commit();
        }
        catch (ConcurrencyException)
        {
            transaction.Rollback();
            throw;  // 呼び出し元で再試行
        }
        catch
        {
            transaction.Rollback();
            throw;
        }
    }
}
```

### 楽観ロックの競合シナリオ

#### ✓ 正常系

```
時刻 10:30: ユーザーA が ItemList 読み込み
           Items.RowVersion = 2026-08-08 10:30:00
           
時刻 10:31: ユーザーA が価格を更新
           UPDATE ... WHERE row_version = 2026-08-08 10:30:00
           ✓ 成功
           Items.RowVersion = 2026-08-08 10:31:00（DB が自動更新）
```

#### ❌ 競合検出

```
時刻 10:30: ユーザーA が ItemList 読み込み
           Items.RowVersion = 2026-08-08 10:30:00
           
時刻 10:31: ユーザーB が同じアイテムを更新
           UPDATE ... WHERE row_version = 2026-08-08 10:30:00
           ✓ 成功
           Items.RowVersion = 2026-08-08 10:31:00（DB が自動更新）
           
時刻 10:32: ユーザーA が価格を更新
           UPDATE ... WHERE row_version = 2026-08-08 10:30:00
           ✗ 失敗（row_version が異なる）
           ConcurrencyException スロー
           → ユーザーA は最新データを再度読み込んで対応
```

### トランザクション分離レベル

推奨: **IsolationLevel.ReadCommitted**

```csharp
using var transaction = _connection.BeginTransaction(
    IsolationLevel.ReadCommitted
);
```

| 分離レベル | 使用場面 |
|---------|---------|
| **Read Uncommitted** | ❌ 非推奨（Dirty Read 発生） |
| **Read Committed** | ✅ 推奨（row_version で競合検出） |
| **Repeatable Read** | △ 複数テーブル集約で厳密性重視の場合 |
| **Serializable** | △ 最高の安全性が必要な場合 |

### ライフサイクル図

```
【参照フェーズ】トランザクションなし
├─ SELECT Items, ItemNames
├─ row_version 取得（Items: 10:30:00, ItemNames: 10:29:50）
└─ Entity 構築、AggregateRoot に組み立て

      ↓ ビジネスロジック実行（トランザクション外）

【保存フェーズ】トランザクション開始
├─ BEGIN TRANSACTION (Read Committed)
├─ UPDATE Items WHERE row_version = 10:30:00
│  └─ ✓ 成功 → row_version 自動更新 (10:31:00)
├─ UPDATE ItemNames WHERE row_version = 10:29:50
│  └─ ✓ 成功 → row_version 自動更新 (10:31:01)
└─ COMMIT

      または

├─ UPDATE Items WHERE row_version = 10:30:00
│  └─ ✗ 失敗（他プロセスが更新）
├─ ROLLBACK
└─ ConcurrencyException スロー
```

### 実装チェックリスト

- [ ] **参照時**: トランザクション開始しない
- [ ] **参照時**: row_version を Entity に保持する
- [ ] **保存時**: トランザクション内で実行
- [ ] **保存時**: IClock を注入して LocalDateTime を取得
- [ ] **保存時**: LocalDateTime.Value で DateTime に変換して DB に保存
- [ ] **保存時**: row_version を WHERE 句で チェック
- [ ] **保存時**: rows_affected == 0 で ConcurrencyException スロー
- [ ] **複数テーブル**: 全テーブルの更新が成功するか、全部失敗するか（原子性）
- [ ] **エラーハンドリング**: ConcurrencyException で呼び出し元が再試行
- [ ] **LocalDateTime 規則**: CreatedAt/UpdatedAt/DeletedAt は Entity では LocalDateTime を使用（CLAUDE.md 準拠）
