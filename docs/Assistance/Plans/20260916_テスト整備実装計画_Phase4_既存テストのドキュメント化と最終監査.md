# Phase 4: 既存テストのドキュメント化・最終監査 実装計画

**作成日:** 2026-09-16
**対象読者:** 本タスクを実装する担当者（人間 または 別セッションのAIエージェント）
**位置づけ:** テスト・テスト仕様書整備プロジェクトの Phase 4。**Phase 0〜3 が完了した後**の仕上げ工程。Phase 0〜3で「テストコードは既存だがドキュメントが個別に触れられていない」クラスの取りこぼしを横断的に洗い出し、最後に全体の整合性を監査する。

---

## 0. 背景・目的

Phase 0〜3 は BC（Bounded Context）や層ごとに個別のクラスを列挙して対応する形式のため、調査時点（2026-09-16）で見つけきれなかった「テストコードは存在するがドキュメントが無い」クラスが取りこぼされる可能性がある。本Phaseでは:

1. SharedKernel の Entity/AggregateRoot ドキュメントの命名規則不整合を解消する
2. Phase 0〜3 完了後に、機械的な差分チェックで「テストコードはあるがドキュメントが無い」「ドキュメントはあるがテストコードが無い」クラスが残っていないか最終監査する
3. 全体を通してのドキュメント配置パス・命名の一貫性を最終チェックする

---

## 1. SharedKernel Entity/AggregateRoot ドキュメントの命名規則統一

**現状:** `docs/SharedKernel/Entity_And_DomainEvents/Entity_And_DomainEvents_単体テスト仕様.md` というファイルが、`Entity<TId>`（`src/SharedKernel/Entities/Entity.cs`）と `AggregateRoot<TId>`（`src/SharedKernel/Entities/AggregateRoot.cs`）の両方のテスト（`tests/SharedKernel.Tests/Entities/EntityTests.cs`, `tests/SharedKernel.Tests/Entities/AggregateRootTests.cs`）をまとめて1ファイルで扱っている。ファイル名も `_単体テスト仕様.md`（末尾に「書」が無い）であり、他の単体テスト仕様書の命名規則（`{ClassName}_単体テスト仕様書.md`）と異なる。

**判断が必要な点（実装者が判断すること）:**
- (a) 現状維持（Entity + AggregateRoot + DomainEventsをまとめて解説する方が、3者の関係性を説明しやすいという合理性がある）
- (b) テンプレート命名規則に合わせて `Entity_単体テスト仕様書.md` と `AggregateRoot_単体テスト仕様書.md` に分割する

**推奨: (a) 現状維持。** 理由: `Entity`/`AggregateRoot`/`IDomainEvent`は密接に関連する基盤型であり、統合ドキュメントの方が可読性が高い。ただし以下の軽微な修正は行う:
1. ファイル名を `Entity_And_DomainEvents_単体テスト仕様書.md`（末尾に「書」を追加）にリネームし、他の単体テスト仕様書と同じ命名規則に揃える。
2. ファイル内に「本書は `Entity`/`AggregateRoot` の統合ドキュメントである」旨を明記し、個別クラス名での検索性を担保する（ドキュメント冒頭に対象クラス一覧を明記）。

## 2. 最終監査: テストコード ⇔ ドキュメントの機械的突合せ

Phase 0〜3 完了後、以下の手順で最終監査を行い、取りこぼしが無いか確認する。

### 2-1. 「テストコードはあるがドキュメントが無い」クラスの洗い出し

```bash
# 全テストクラスファイルを列挙（.vshistory/bin/obj除く）
find tests -name "*Tests.cs" -not -path "*.vshistory*" -not -path "*/bin/*" -not -path "*/obj/*" | sort

# 全単体テスト仕様書ドキュメントを列挙
find docs -iname "*単体テスト仕様書*.md" | sort
```

両方の一覧を突き合わせ、テストファイル名（`{ClassName}Tests.cs`）に対応する `{ClassName}_単体テスト仕様書.md` が存在しない、または統合ドキュメント（`Application_単体テスト仕様書.md`, `Infrastructure_単体テスト仕様書.md`, `Entity_And_DomainEvents_単体テスト仕様書.md` 等）の中で言及されていないクラスをリストアップする。

見つかった場合、該当クラスのテストコードを `Read` し、Phase 2/3 と同じ要領で該当BC/層のドキュメント（既存の統合ドキュメントがあれば追記、無ければ新規作成）に追加する。

### 2-2. 「ドキュメントはあるがテストコードが無い／対象クラスが実在しない」ケースの洗い出し

各単体テスト仕様書の「2. テスト対象クラス」表に記載のクラス名について、対応する `src/` 配下のクラスファイルと `tests/` 配下のテストファイルが実在するか確認する。特に以下のパターンに注意する（Phase 0で実際に見つかったパターン）:

- クラスが別の Bounded Context に移設された後もドキュメントが古い場所に残っている（Phase 0-3で対応したDepartment関連の5件と同じパターン）
- ドキュメントのテストケース名・件数が、実際のテストコードのメソッド名・件数と乖離している

不整合が見つかった場合、実際のソース・テストコードを正としてドキュメントを修正する（ルートCLAUDE.mdの「ドキュメントと実コードが矛盾する場合、実コードを正としてドキュメントを直す」の原則に従う）。

### 2-3. Bounded Context 単位の完全性チェックリスト

以下の表がすべて「テスト:済み」「ドキュメント:済み」になっていることを最終確認する（Phase 0〜4完了後の期待状態）。

## 3. 参考情報: Architecture.Tests の拡充候補（任意対応）

本Phaseの主目的ではないが、調査時に判明した `tests/Architecture.Tests` のギャップを参考情報として記録する。余力があれば対応する。

- `BoundedContextIsolationTests.cs`（`tests/Architecture.Tests/BoundedContextIsolationTests.cs`）に `Department` BC と `IntegrationPrototype` BC の分離チェックが無い（`CarPreferences`/`Authentication`/`Employee` の組み合わせのみ検証されている）
- `LayerDependencyTests.cs` の `Presentation_ShouldNotDependOnInfrastructureImplementations` は汎用 `SupportAdvance.Infrastructure.*` 名前空間のみを見ており、Context別Infrastructure（`SupportAdvance.Contexts.Authentication.Infrastructure` 等）への直接参照は検出できない

対応する場合は既存の `DependencyRuleTests.cs`/`LayerDependencyTests.cs`/`BoundedContextIsolationTests.cs` の実装パターン（`NetArchTest.Rules`）を踏襲してテストケースを追加する。
