## 現状分析

### 調査で判明した事実

Skip 属性のコメントには「要DB接続。Phase 5で結合テストとして再設計」と記載されているが、実際に調査した結果、**2種類の異なる性質のテストが混在**していることが判明した。

#### 分類 A: Application.Tests（DB接続不要 — 誤った前提でSkip）

`CreateEmployeeUseCaseTests` 等の `MockEmployeeRepository` は以下のような **ダミー実装** になっている：

```csharp
private class MockEmployeeRepository : IEmployeeRepository
{
    public Task AddAsync(Employee employee) => Task.CompletedTask;          // 何もしない
    public Task<Employee?> GetByIdAsync(EmployeeRowId id) => Task.FromResult<Employee?>(null);  // 常に null
    ...
}
```

UseCase はリポジトリの **インターフェース** にのみ依存しており、実際のDB接続を必要としない。`MockEmployeeRepository` を「インメモリで実際に状態を保持する実装」に差し替えるだけで、DB接続なしにテスト可能。

**動作確認済み**: `EmployeeDtoMappingTests`（3件）は Skip を外すだけで **3/3 成功** することを確認済み（DTO設計は既に完了していた）。

#### 分類 B: Infrastructure.Tests（本当にDB接続が必要）

`EmployeeRepositoryTests` / `DepartmentRepositoryTests` は **Repository の実装自体**（Dapper/RepoDb 経由の実SQL実行）を検証するテストであり、これは本当に SQL Server（または代替のテストDB）が必要。Department Context も同じ理由で Phase 5 送りにされている（既存の前例）。

### Phase 5-B: Infrastructure.Tests の真の結合テスト（既存開発DBを使用）

対象：Employee.Infrastructure.Tests（11件）+ Department.Infrastructure.Tests（10件）

**方針決定：** 既存の開発DB（`3160EPOTAK` / `SupportAdvance`、`appsettings.Debug.json` に設定済み）を共用する。新規テスト環境は構築しない。

#### 追加調査で判明した重大な事実

Repository の実装状況を調査した結果、**Department と Employee で実装完成度が大きく異なる**ことが判明した。

| Context | Repository実装状況 |
|---|---|
| **DepartmentRepository** | ✅ 完全実装（GetByIdAsync / GetByCodeAsync / GetAllAsync / SaveAsync / DeleteAsync） |
| **EmployeeRepository** | ⚠️ 一部未実装：`AddAsync` `DeleteAsync` `GetByPersonRowIdAsync` が `NotImplementedException` |

Employee.Infrastructure.Tests の11件は **ほぼ全てが Arrange 部分で `repository.AddAsync()` を呼んでいる** ため、AddAsync 実装なしには実行不可能。したがって Phase 5-B は「Skip解除」だけでは完結せず、**Repository実装の完成**が前提作業として必要になる。

#### Phase 5-B の作業内訳

**B-1. テストデータ汚染防止策の設計（両Context共通）**

開発DBを共用するため、以下の対策を実施する：
- RowId は Application.Tests の `MockSequenceProvider` と同じ方式で、テスト専用の高い範囲（`2147483648` 以降）を使用し、既存データと衝突させない
- 各テストクラスに `IAsyncLifetime`（xUnit）を実装し、`DisposeAsync` でテスト中に作成したデータを確実に削除する（生成した RowId を記録しておき、テスト終了時に物理削除）
- Employee は `m_employees` + `m_persons` の2テーブルに依存するため、クリーンアップは両方を対象にする

**B-2. EmployeeRepository 未実装メソッドの実装**

`DepartmentRepository.SaveAsync`（新規/更新を1メソッドで判定するパターン）ではなく、既存の Employee 設計（`AddAsync` / `UpdateAsync` 分離、`UpdateAsync` は実装済み）に合わせて実装する。

1. **AddAsync**：
   - `EmployeeMapper.ToDbModel(employee)` で `EmployeeDbModel` 生成、`ToPersonDbModel(employee.Person, ...)` で `PersonDbModel` 生成（既存メソッドを利用）
   - `CreatedAt` / `CreatedBy` を Repository で設定（Mapper では設定しない、既存規約に準拠）
   - トランザクション内で `m_employees` → `m_persons` の順に RepoDb `InsertAsync`
   - `DepartmentMemberships` があれば同一トランザクションで INSERT
   - 参考実装：既存の `UpdateAsync`（本ファイル250行目〜）のトランザクション構造をそのまま踏襲

2. **DeleteAsync**：
   - `DepartmentRepository.DeleteAsync`（論理削除パターン）を参考に、`DeletedAt` / `DeletedBy` を設定して `UpdateAsync` 相当の処理を実行

3. **GetByPersonRowIdAsync**：
   - `GetByIdAsync` と同様のクエリ構造で、`PersonRowId` を条件に `m_employees` を検索するSQLを追加（`Employees.GetEmployeeByRowId` に相当する新規SQLファイルが必要）
   - 複数件ヒットしうるため `QueryAsync`（`QueryFirstOrDefaultAsync` ではない）

**B-3. Department 結合テストの有効化**

Repository は実装済みのため、以下のみで着手可能：
- `DepartmentRepositoryTests.cs` の `CreateRepository()` を実際の `DepartmentRepository`（DI経由、`appsettings.Debug.json` の接続文字列使用）に差し替え
- B-1 のクリーンアップ機構を追加
- Skip 属性を削除して実行確認

**B-4. Employee 結合テストの有効化**

B-2 の実装完了後：
- `EmployeeRepositoryTests.cs` の `CreateRepository()` を実際の `EmployeeRepository` に差し替え
- B-1 のクリーンアップ機構を追加（Person テーブルも対象）
- Skip 属性を削除して実行確認

## リスクと注意事項

- **開発DB共用のリスク**：テスト実行タイミングで他の開発者が同DBを使用していると干渉の可能性がある。RowId範囲分離とクリーンアップの徹底で緩和するが、完全な隔離ではない点に留意
- **EmployeeRepository 実装の影響範囲**：新規実装がプロダクションコードの変更にあたるため、Employee.Application 側（CreateEmployeeUseCase 等）の動作確認も合わせて行う
- **接続文字列の扱い**：`appsettings.Debug.json` に平文パスワードが含まれている。今回のスコープでは変更しないが、認識のうえ取り扱う
