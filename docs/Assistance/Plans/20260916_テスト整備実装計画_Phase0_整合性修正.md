## 0. 背景・目的

`D:\SupportAdvance` は .NET のクリーンアーキテクチャ構成のソリューションで、`docs/Assistance/Templates/Test/` に単体テスト仕様書テンプレート5種（ValueObject / Entity / DomainService / UseCase / 汎用）と結合・システムテスト仕様書テンプレートが用意されている。

全ソースコードを対象にテストコード・テスト仕様書の棚卸し調査を行った結果、実装作業（新規テスト追加）に着手する前に **先に直しておくべき欠陥** が複数見つかった。これらを放置したまま Phase 1 以降（新規テスト・ドキュメント追加）を進めると、壊れた土台の上に積み増すことになるため、最初に本 Phase 0 で解消する。

### 本Phaseのゴール

1. `SupportAdvance.slnx` に登録されているテストプロジェクトが実際に**すべてビルド可能**な状態にする
2. テストファイル名と実際の検証対象が一致しない状態を解消する
3. Bounded Context 分割（Department を Employee から切り出した際）で取り残された、内容の古いドキュメントを正しい場所・内容に修正する
4. 現在のコードに存在しない孤立したテストコードや、実体のないドキュメント参照を削除する

**現状（2026-09-16 時点で実際に `dotnet build` して確認済み）:**

### 0-2. `SequenceProviderTests.cs` の対象クラス不一致の修正

**現状:** `tests/Infrastructure.Tests/Providers/SequenceProviderTests.cs` は、ファイル名・クラス名 (`SequenceProviderTests`) から `SupportAdvance.Infrastructure.Providers.SequenceProvider`（`src/Infrastructure/Providers/SequenceProvider.cs`）を検証しているように見えるが、実際にはファイル内部で private に定義した `MockSequenceProvider`（`ISequenceProvider` を実装したテスト専用のインメモリ実装）しか検証していない。本物の `SequenceProvider`（SQL Server の `dbo.s_row_id_sequence` に対して `SqlConnection` で直接 `SELECT NEXT VALUE FOR` を実行する実装）は一度もテストされていない。

**`SequenceProvider` の実装詳細（`src/Infrastructure/Providers/SequenceProvider.cs`）:**
- コンストラクタは `IAppSettings appSettings` を受け取り、`appSettings.ConnectionStrings` から `"Default"` → `"SupportAdvance"` → 最初のキー、の優先順位で接続文字列を解決する `GetConnectionString`（`private static`）を持つ
- `GetNextValueAsync()` / `GetNextValuesAsync(count)` は `SqlConnection` を new して `SELECT NEXT VALUE FOR [dbo].[s_row_id_sequence]` を実行する。`count <= 0` は `ArgumentException`
- SQL例外は `SequenceProviderException` にラップされる
- 実DB接続なしに `GetNextValuesInternal` 部分（SQL実行そのもの）を単体テストすることはできない

**作業手順:**

1. 既存の `SequenceProviderTests.cs` を **`MockSequenceProviderTests.cs`** にリネームし、クラス名も `MockSequenceProviderTests` に変更する（7つの既存テストメソッドはそのまま維持してよい。`MockSequenceProvider` はテスト専用ダブルとして正当な検証対象である）。ファイル冒頭のXMLドキュメントコメントも「MockSequenceProvider のテスト」である旨を明記する（既に一部そう書かれているので、クラス名との整合性を取るだけでよい）。
2. `GetConnectionString` のフォールバックロジックと `count <= 0` の例外ロジックだけは、DB接続なしに単体テスト可能な「純粋ロジック」である。これをテスト可能にするため、`SequenceProvider.cs` の `GetConnectionString` を `private static` から `internal static` に変更する。
3. `src/Infrastructure/AssemblyInfo.cs` を新規作成し、以下を記述する（`src/SharedKernel/AssemblyInfo.cs` の実装パターンを参考にする。ただし後述の注意点を踏まえ、実際のアセンブリ名を指定すること）:
   ```csharp
   using System.Runtime.CompilerServices;

   [assembly: InternalsVisibleTo("Infrastructure.Tests")]
   ```
   **注意:** `tests/Infrastructure.Tests/Infrastructure.Tests.csproj` に `AssemblyName` の明示的な上書きはなく、既定のアセンブリ名は csproj ファイル名そのまま `Infrastructure.Tests` になる（`RootNamespace` は `tests/Directory.Build.props` で `SupportAdvance.Tests.$(MSBuildProjectName)` に上書きされているが、これは名前空間の話でアセンブリ名とは別）。`InternalsVisibleTo` にはアセンブリ名を指定する必要があるため、`"Infrastructure.Tests"`（`"SupportAdvance.Infrastructure.Tests"` ではない）を指定すること。
   - 参考: 既存の `src/SharedKernel/AssemblyInfo.cs` は `InternalsVisibleTo("SupportAdvance.SharedKernel.Tests")` と書かれているが、`tests/SharedKernel.Tests/SharedKernel.Tests.csproj` にも `AssemblyName` の上書きがなく実際のアセンブリ名は `SharedKernel.Tests` のはずである。**これは恐らく既存の潜在バグ（InternalsVisibleTo が実際には効いていない）だが、本Phaseのスコープ外なので深追いせず、新規に作る `Infrastructure` 側では同じ誤りを繰り返さないことだけ徹底する。** 気になる場合は別タスクとして報告するに留める。
4. 新規に `tests/Infrastructure.Tests/Providers/SequenceProviderTests.cs`（このファイル名を実クラスのテストとして使う）を作成し、`SupportAdvance.Infrastructure.Providers.SequenceProvider` の以下をテストする:
   - `GetConnectionString` 相当のロジック（`internal` 化したメソッドを直接呼ぶ、または `IAppSettings` のテストダブルを用意して `ConnectionStrings` に `"Default"`/`"SupportAdvance"`/その他キーを設定し、優先順位どおりに解決されることをコンストラクタ経由で間接的に検証する）
   - コンストラクタが `appSettings` が null の場合に `ArgumentNullException` を投げること
   - コンストラクタが接続文字列を1つも解決できない場合（`ConnectionStrings` が空）に `InvalidOperationException` を投げること
   - `GetNextValuesAsync(0)` / `GetNextValuesAsync(-1)` が `ArgumentException` を投げること（これは実際に `SqlConnection` を開く前にガードされるため、DB接続なしでテスト可能）
   - 実際に SQL Server に接続してシーケンス値を取得する部分（`GetNextValuesInternal` の中身）は単体テスト不可能なため対象外とし、ファイル冒頭のコメントで「DB接続を要する部分は結合テストで別途検証する（Phase 5参照）」と明記する

