## 1. 結合テスト仕様書の新規作成（DB接続を要する箇所の受け皿）

Phase 0〜3 で以下のクラスは「実SQL Server接続が必要なため単体テストの対象外とし、結合テストで扱う」という方針で保留された。本Phaseでこれらを回収する。

| 対象クラス | 保留元Phase | 検証したい内容 |
|---|---|---|
| `SupportAdvance.Infrastructure.Providers.SequenceProvider` | Phase 0-2 | `GetNextValueAsync`/`GetNextValuesAsync` が実際にSQL Serverの`dbo.s_row_id_sequence`から重複の無い昇順の値を取得できること |
| `SupportAdvance.Contexts.Employee.Infrastructure.Repositories.EmployeeRepository` | Phase 0-1 | Save/Get/Update/Delete の実DB CRUD、複数テーブル（`m_employees`+`m_persons`+`m_department_memberships`）の結合取得、監査フィールドの自動設定 |
| `SupportAdvance.Contexts.Department.Infrastructure.Repositories.DepartmentRepository` | Phase 1 | 同上（Department版） |
| `SupportAdvance.Contexts.Authentication.Infrastructure.Repositories.UserAuthSessionRepository` | Phase 3 | Save/Get/GetLatest/Update の実DB CRUD |

**作業手順:**

1. `docs/Assistance/Templates/Test/TEMPLATE_結合テスト仕様書.md` の「Application ↔ Infrastructure 統合」パターンを使用する。
2. テスト実行に実SQL Server環境（またはDockerによるローカルSQL Server、`docs/`配下に既存のマイグレーションSQLがあれば`src/Contexts/*/Infrastructure/Migrations/`を参照してテスト用スキーマを作る）が必要になる。既存の結合テスト実行環境（CI設定、ローカル開発手順）がリポジトリ内に無いか事前に `docs/Assistance/Guides/` や `.github/workflows/`（存在すれば）を確認すること。無ければ、本Phaseの中で「結合テスト実行手順書」を1つ `docs/Assistance/Guides/結合テスト実行環境セットアップ.md` として作成することも検討する。
3. 各対象クラスにつき、`tests/*.Tests` 配下に既存の `[Fact(Skip = "...")]` を実装に差し替える、または新規に結合テスト用のテストクラス（例: `SequenceProviderIntegrationTests.cs`）を作成する。xUnitの `[Trait("Category", "Integration")]` 等で単体テストと区別し、通常の `dotnet test` では除外できるようにする（例: `dotnet test --filter "Category!=Integration"` で単体テストのみ実行できるようにする運用を推奨）。
4. ドキュメントは以下に配置する:
   - `docs/Infrastructure/Providers/SequenceProvider_結合テスト仕様書.md`
   - `docs/Contexts/Employee/Infrastructure/EmployeeRepository_結合テスト仕様書.md`
   - `docs/Contexts/Department/Infrastructure/DepartmentRepository_結合テスト仕様書.md`
   - `docs/Contexts/Authentication/Infrastructure/UserAuthSessionRepository_結合テスト仕様書.md`

## 2. システムテスト仕様書の新規作成（BC単位、最低1本ずつ）

`docs/Assistance/Templates/Test/TEMPLATE_システムテスト仕様書.md` を使用し、各 Bounded Context について「複数UseCaseにまたがる業務シナリオ」を最低1本ずつ作成する。

### 2-1. Employee BC

シナリオ例: 「従業員の新規登録 → 部署配属 → 情報更新 → 退職処理」という一連の業務フロー。関連UseCase: `CreateEmployeeUseCase` → （部署配属は `DepartmentMembership` 追加、該当UseCaseがあれば）→ `UpdateEmployeeUseCase` → `Employee.RetireEmployee()`（`EmployeeRetiredEvent`発行の確認も含める）。

配置先: `docs/Contexts/Employee/Employee_システムテスト仕様書.md`

### 2-2. Department BC

シナリオ例: 「部署の新規作成 → 上位部署への紐付け（`ParentDepartmentRowId`）→ 管理者従業員の割当（`ManagerEmployeeRowId`、Employee BCとの連携確認）→ 廃止」。Department BCとEmployee BCの連携は `IQueryService<Employee, EmployeeRowId>` 等のジェネリック Query Service パターン（ルートCLAUDE.mdの「Context間のデータ共有パターン」参照）経由であることを確認する。

配置先: `docs/Contexts/Department/Department_システムテスト仕様書.md`

### 2-3. Authentication BC

シナリオ例: 「ログイン試行 → 認証成功 → セッション発行 → セッションを使った操作 → ログアウト」。および「認証失敗（パスワード不一致）のフロー」。`AuthenticateLocalUserUseCase` → `UserAuthSession` 発行 → `LogoutUseCase` の一連の流れ。

配置先: `docs/Contexts/Authentication/Authentication_システムテスト仕様書.md`

## 3. 検証方法

```bash
dotnet build --no-incremental
dotnet test --filter "Category!=Integration"   # 単体テストのみ（CI等日常実行用）
dotnet test                                       # 結合テスト含め全件（実SQL Server環境が必要）
```

- 結合テストが実DB環境無しでは失敗する場合、その旨と必要な環境セットアップ手順がドキュメント・テストコードのコメントに明記されていること
- システムテスト仕様書は、実際にテストコードとして実装するかどうかは本Phaseの必須要件としない（仕様書の策定を優先し、実装は後続タスクとしてよい）。ただし実装した場合は対応するテストプロジェクト（例: `tests/SystemTests/` を新設）を `.slnx` に登録することを忘れないこと（Phase 0で繰り返し発生した「登録漏れ」を再発させない）

## 4. 本Phase完了をもって、全体計画（Phase 0〜5）は完了とする

Phase 0〜5がすべて完了した時点で、以下が達成されている状態になる:

- `SupportAdvance.slnx` に登録された全テストプロジェクトがビルド・実行可能
- Domain/Application/Infrastructure の主要クラスに単体テストと対応するテンプレート準拠のドキュメントが存在
- DB接続を要する箇所は結合テストとして明示的に区別されている
- BC単位のビジネスシナリオを検証するシステムテスト仕様書が最低1本ずつ存在
