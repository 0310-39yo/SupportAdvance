## フェーズ 4: `DateTime` の Domain / SharedKernel からの排除（D1）

Domain の VO が DB の型（`DateTime`）を知っている状態をなくし、変換を Infrastructure に集約する。**フェーズ 5 の新しい VO が最初から新ルールに従えるよう、先に行う。**

### 4-A. 変換の窓口を Infrastructure に用意する

- 汎用 `src/Infrastructure`（Mapper 群のある場所）に、`DateTime` ↔ `LocalDateTime` の変換ヘルパー（拡張メソッド）を追加
  - **名称は確定（フェーズ 1 のドキュメントで使用済み）**: `DateTime.ToLocalDateTime()`（→ `LocalDateTime`。NOT NULL の列用）、`DateTime?.ToLocalDateTimeOrNull()`（→ `LocalDateTime?`）。`LocalDateTime` → `DateTime` は既存の `LocalDateTime.Value` を使い、ヘルパーは作らない
  - 置き場所の候補: 汎用 `src/Infrastructure/Mappers/`（例: `DbDateTimeExtensions`）。名前空間は `SupportAdvance.Infrastructure.Mappers`
  - Context 別 Infrastructure は汎用 Infrastructure を既に参照している（依存方向は許可済み）
- 単体テストを追加（`Infrastructure.Tests`）

### 4-B. 8 つの VO から DateTime 受け渡しメソッドを削除

| VO | 場所 | 削除するメンバー |
|---|---|---|
| `CreatedAt` / `UpdatedAt` / `DeletedAt` | SharedKernel | `FromDbValue(DateTime)`、`TryFromDbValue(DateTime?)`、`ToDbValue()` |
| `AbolishedOn` | Department.Domain | `TryFromDbValue(DateTime?)` |
| `RetiredOn` / `EndOn` / `ExpirationOn` / `EffectiveAt` | Employee.Domain | `TryFromDbValue(DateTime?)`（`EffectiveAt` は非 null 版） |

Domain 側の入口は既にある `From(LocalDateTime)` / `TryFrom(LocalDateTime?)` を使う（未設定は `Unset()`）。

### 4-C. 呼び出し側を Mapper / Repository の変換に置き換える

| 箇所 | 変更 |
|---|---|
| `EmployeeRepository`（監査値の読み込み 12 箇所） | `UpdatedAt.TryFromDbValue(dbModel.UpdatedAt, ...)` → `UpdatedAt.TryFrom(dbModel.UpdatedAt.ToLocalDateTimeOrNull(), ...)` |
| `DepartmentMapper:60` | `AbolishedOn.TryFrom(dbModel.AbolishedOn.ToLocalDateTimeOrNull(), ...)` |
| `EmployeeMapper` | `RetiredOn` / `EndOn` / `ExpirationOn` / `EffectiveAt` の生成を同様に変換。`ToDbModel` 側の `.Value.Value` も変換ヘルパーに統一 |
| 他の Repository（Department / Authentication）| 監査値を VO と行き来している箇所があれば同様に修正（着手時に grep で全件確認） |

### 4-D. テスト

- 削除: 各 VO の `TryFromDbValue` / `FromDbValue` / `ToDbValue` を検証していたテスト（`CreatedAtTests` 18、`UpdatedAtTests` 28、`DeletedAtTests` 28、`AbolishedOnTests` 4 ほか）のうち該当ケース
- 移設: 「DB の null → Unset」「DB 値 → VO」の検証は、Mapper / Repository / 変換ヘルパーのテストで再現（観点は落とさない。テスト観点 ID の統一運用に従う）

## リスクと注意

- **DB スキーマは変更しない**（DbModel は `DateTime?` / `long?` のまま。変換は Mapper / Repository が行う）
- フェーズ 4 は監査値（`CreatedAt` など）の読み書きに広く関わる。Repository の監査値の設定は Repository の責務のまま（Mapper に移さない）。変換ヘルパーを使うだけにとどめる
- 5-B は `UserAuthSession` の生成 API（ファクトリ・`Reconstruct`）の署名が変わる。UseCase の呼び出し側を同時に直す
- 5-C は `Department` 集約と Employee 集約の両方に触れる。BC 間の直接参照は作らない（VO は SharedKernel 経由で共有）
- 7-3・7-6 は `RowVersion`（`byte[]`）などの技術的な項目を許可リストに入れないと誤検知する
- 既存の DB 統合テストは実 DB（`s_test_row_id_sequence`）を使う。テスト規約（固定 ID・範囲削除の禁止）を守る
